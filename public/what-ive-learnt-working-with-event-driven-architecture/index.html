Over the last few months I've been getting to work with an event-driven architecture system built with AWS EventBridge. It has led me to think more about the design choices that go into a system like this compared to a more traditional approach. In this post I’m writing about what event-driven architecture is, how EventBridge fits into it, and some of the benefits and trade-offs I've come across.

Photo by Sebastian Schuster on Unsplash

What is it?

Event-driven architecture (EDA) is a software design pattern where components communicate by producing and reacting to events. Events are records that something has happened, for example, an order has been placed or a user has signed up.

The key idea behind EDA is decoupling. In a traditional request/response design, services call each other directly and depend on one another's responses. This means that a failure in one service can break the whole chain. In EDA, a producer publishes an event without knowing or caring who consumes it. Each consumer reacts to that event independently.

Producers, consumers, and the event broker

These three form the basis of every event-driven system: something happens, it gets announced, and other parts of the system react.

  1. Producers detect that something has happened and publish an event about it. An event describes what happened but not what should be done about it.
  2. Consumers subscribe to the events they care about and react to them. Several consumers can react to the same event in different ways.
  3. The event broker sits in the middle, receiving events from producers and delivering them to consumers. Producers and consumers only need to know about the broker and not each other.

Using EventBridge

The system I've been working on uses AWS EventBridge, which is an event bus. Producers put events onto the bus and rules match on the content of each event. Rules then route each event to one or more targets such as a Lambda function or an SQS queue. Failed deliveries are retried, and you can set up a dead-letter queue (DLQ) for events that keep failing.

A dead-letter queue keeps any event that couldn't be delivered to its target after all the retries, instead of it being silently dropped. You can then look at what failed and why, fix the underlying problem, and reprocess the events.

Benefits

There are many benefits to using event-driven architecture. The main one is loose coupling, as services can be built, deployed, and scaled independently. This makes systems more extensible, meaning that you can add a new consumer without changing the producer or any existing code. It also helps with resilience, as a slow or crashed consumer doesn't block the producer or other consumers.

What can go wrong

With any system design, there are trade-offs. For a simple CRUD application, event-driven architecture is probably overkill. There can also be issues with eventual consistency, as different parts of the system aren't updated at the same moment. Consumers also need to be idempotent (meaning that processing the same event twice has the same result as processing it once), as events can be delivered more than once.

Event-driven architecture is a useful design pattern to know, and it's a good fit when you expect to keep adding new behaviour over time, or you don't want a slow or unreliable consumer affecting everything else. It isn't the right choice for every system, however, and the extra complexity needs to be worth what you get in return. Like every decision in software design, it's important to understand the trade-offs and be intentional about where events genuinely help.
